# Encryptor 安全审计报告（红队攻防实测）

- 日期：2026-10-09
- 对象：Encryptor v1.0.0（commit c931d05），Python 3.13.5 / cryptography 44.0.1 / gmssl 3.2.2
- 审计性质：**授权的内部红队测试**。攻击者模型：无任何社会工程（不窃取口令/私钥文件），
  仅通过技术手段攻击软件本身与其加密产物。
- 复现方式：`attack_lab/` 下全部脚本可直接运行（`python a1_container.py` 等）。

## 一、总体结论（TL;DR）

对终极问题"**任意一份非空密文能否被技术性破密**"的回答：

| 插件 | 机密性 | 结论 |
|------|--------|------|
| **sm2-sm4-gcm** | 🔴 **已被完全破密** | 见发现 F1：私钥/临时密钥 k 由 Mersenne Twister 生成，攻击者可精确预测私钥并完整解出明文（已实测演示） |
| aes-256-gcm / sm4-gcm / rsa / ecdh（强凭据） | ✅ 未破 | 格式层无泄露，算法使用正确，未找到密码学破绽；安全边界 = 口令强度 / 私钥文件保密 |
| 全部密码插件（弱口令） | ⚠️ 可离线爆破 | KDF 迭代偏低（见 F4），弱口令秒级破出 |

**完整性层面**：全部 4 个 GCM 插件存在**无声截断攻击**（发现 F2）；流密码插件无认证（软件已声明，属已知限制）。

防御做得好的方面（实测确认）：密文统计随机、无明文残留、盐/nonce/CEK 每次全新、
无密钥流复用、块重排被拒、容器模糊测试全部正确拒绝、`.part` 无残留、
ECDH 插件的临时公钥有在曲线校验、内存清零机制实测有效。

## 二、发现清单（按严重度）

### F1 🔴 严重：SM2 插件使用非密码学随机数（Mersenne Twister）——已实现完全破密

**位置**：
- `plugins/sm2_hybrid/plugin.py:107`（私钥生成 `gm_func.random_hex`）
- gmssl `sm2.py CryptSM2.encrypt`（临时密钥 k 同样来自 `func.random_hex`）
- 根因：`gmssl/func.py` 定义 `random_hex = lambda x: ''.join([choice('0123456789abcdef') for _ in range(x)])`，
  `choice` 来自 **Python `random` 模块 = MT19937**，非 CSPRNG。

**影响**：SM2 长期私钥与每次加密的 k 完全依赖 MT19937。MT 状态仅 19937 位且可被完整克隆：
同一进程内任何其它代码消费过 `random` 且输出可观察（日志、会话号、采样值——Python
生态极常见），624 个 32 位输出即可恢复状态，此后**同进程内生成的一切 SM2 私钥与 k
全部可预测**。这违反 GM/T 0003 对随机数的基本要求。

**实测（attack_lab/a3_mt.py）**：
受害者子进程（真实软件、真实引擎）：泄漏窗口（624×`getrandbits(32)`）→
`generate_keypair()` 生成密钥 → 加密机密文件。攻击者进程仅凭
`observed.bin` + `intercepted.encx`：

```
预测出的受害者 SM2 私钥 d = 0xf05b9ec23db61e2f...
SM3(解出的CEK) == 元数据校验值 ? True
破密得到明文(169B): SM2-MT 攻击演示明文：导弹发射代码 ALPHA-773492 ...
★ 完全破密成功 = True
★ 预测私钥 == 真私钥 ? True
```

**修复**（优先级最高）：
1. 私钥生成改用 `os.urandom(32)`（或在 [1, n-1] 内重采样）：
   ```python
   while True:
       d = int.from_bytes(os.urandom(32), "big")
       if 1 <= d < n: break
   ```
2. 加密侧临时 k：不能依赖 gmssl 内部的 `random_hex`。建议在插件内自实现 SM2 加密
   （曲线参数公开，`_kg` 可复用），k 取 `os.urandom(32) mod (n-1) + 1`；
   或给 gmssl 打补丁/更换为带正确 RNG 与点校验的 SM2 实现。
3. 顺带修复 F3（C1 校验）。

### F2 🟠 高：全部 GCM 插件可被"无声截断"——元数据总长字段未认证

**位置**：aes256_gcm / sm4_gcm / rsa_hybrid / ecdh_hybrid / sm2_hybrid 的
`encrypt_stream` 把"明文总长度(8B)"放进**未认证**的尾部元数据；解密仅
在最后比对 `total != expect_total`。所有 GCM 块的 AAD 均为 `None`。

**攻击（attack_lab/a5_integrity.py A）**：删除末尾若干整块密文（每块 1MiB+16B），
并把元数据中的总长改成截断后的值 → 受害者**正常解密、无任何告警**：
```
aes-256-gcm: 原明文 3,145,729B → 篡改为 3,145,728B → 解密"成功"，无声丢失数据
（rsa / sm4 / sm2 同样成功；ecdh 结构相同亦适用）
```
危害：攻击者（或坏块介质）可让"完整密文"解出被裁剪的内容而用户毫无察觉——
对合同、账目类文件是实质威胁。

**修复**：把总长度（以及 salt/nonce_prefix/wrapped CEK 等全部元数据）作为
**AAD** 绑进每个 GCM 块：`cipher.encrypt(nonce, chunk, aad=metadata)`；
或把元数据哈希放入 AAD。这样改写任何一个字段都会导致第一块即认证失败。

### F3 🟠 高：SM2 解密不校验 C1 在曲线上（GB/T 32918 强制要求）+ 畸形密文引发内部崩溃

**位置**：gmssl `CryptSM2.decrypt` 直接 `_kg(d, C1)`；插件未做补充校验。

**实测（attack_lab/a4_invalid_curve.py）**：
- 任意伪造的 C1（不在任何曲线上）被直接接受参与运算——受害者软件对攻击者
  完全可控的恶意 `.encx`（空载荷 + `expect_total=0`）报告"**解密完成**"；
- 特定无效点让真实软件抛出内部 `TypeError('NoneType' object is not subscriptable)`
  （包装成 IntegrityError，用户可见混乱的内部错误信息）——健壮性缺陷；
- 经典 Biehl–Meyer–Müller 小阶无效曲线**密钥恢复**：本环境实测被 gmssl 的
  纯 Python 算术意外阻断（40 个随机密钥 0 个"干净路径"，中间命中无穷远点产生
  确定性乱码）。**不能依赖这个侥幸**：换实现/修好算术后攻击立即成立。
- 对照：ecdh 插件所用 cryptography 库的 `from_encoded_point` 会拒绝曲线外的点
  （实测 ValueError），是正确做法。

**修复**：解密前校验 C1：`0 <= x,y < p` 且 `y² ≡ x³ - 3x + b (mod p)`（b 为
标准曲线参数），不通过直接抛 IntegrityError；同时捕获 gmssl 内部异常给出干净报错。

### F4 🟡 中：口令 KDF 迭代偏低 + 无口令强度策略

**实测（attack_lab/a2_kdf.py）**：本机 CPU 单核 PBKDF2-HMAC-SHA256×200k =
21 H/s（SM3 版仅 6 H/s）。弱口令（`123456`）在 12 词字典中 0.3s 破出。
单张 RTX 4090 跑 hashcat 约 3–5k H/s：8 位小写字母口令期望 ~1 年/卡，
8 卡集群 ~40 天。OWASP 2023 起 PBKDF2-SHA256 建议 ≥600k。

**修复**：迭代提到 600k（或换 Argon2id）；GUI 增加口令强度提示/最小长度；
文档明示"机密性上限 = 口令熵"。

### F5 🟡 中：流密码插件（xor-stream / sm3-stream）完全无完整性、错口令无检测

**实测（a5 C/D）**：
- 定向比特翻转：明文 `03:00` → `09:30` 精确篡改，解密"成功"无告警（软件已声明此限制）；
- 头部插件 id 交换（xor↔sm3，两者元数据布局同为 16B 盐）：错误算法解密**静默输出乱码**，
  用户可能把乱码当损坏数据覆盖原文件。
- 错误口令同样静默输出乱码（无 WrongPassword 检测）。

**修复**：至少在尾部追加一个 `SM3(密文||盐)` 校验和；更彻底的做法是给这两个
"教学插件"叠一层 HMAC。错口令/错算法即可被立即检出。

### F7 🟠 高：内存镜像取证攻击——使用后密钥材料物理残留（实测确认）

**方法（attack_lab/a7_memdump.py, a7b_locate.py）**：受害者子进程用真实引擎完成
加密+解密后保持存活（模拟"软件用完还开着"）；**外部进程**做
`MiniDumpWithFullMemory` 全内存镜像（procdump -ma 同款，受害者零扰动，
排除了同进程扫描"边扫边覆盖"的假阴性）；离线搜索密钥材料的全部内存表示
（raw 大端 / OpenSSL BIGNUM 小端 limb / hex·HEX ASCII 串 / UTF-8 口令），
每个插件单独跑一轮 + 全插件混跑 + 每场景 3 轮一致性验证。

**结果**：

| 密钥材料 | 残留情况 |
|---------|---------|
| 口令（str，文档已声明的限制） | **7/7 场景全部残留**（各 1 份 freed Python str；GUI StringVar 还会常驻活副本） |
| **ECC 私钥标量（长期私钥！）** | **3 轮中 2 轮残留**。命中处上下文是**完整 PKCS#8 DER**（`30 81 87 … 04 20 ‹32B 私钥› a1 44 03 42 00 04 ‹公钥›`）——`load_pem_private_key` 解析过程产生的 DER 副本释放后未清零；一轮还同时出现 BIGNUM 小端 limb 副本 |
| **SM2 场景 CEK（单文件内容密钥）** | **3 轮中 2 轮残留**（一次 raw、一次 hex 串——gmssl decrypt 内部 `M` 十六进制串即插件注释自认无法清零的副本） |
| AES/SM4/XOR 派生密钥、密钥流 | 0 残留（securemem 清零 + 无持久原生副本，全部表示验证） |
| RSA 私钥 d/p/q | 0 残留（3/3 轮干净——OpenSSL 该路径会清 BIGNUM） |
| 明文 | 残留（文档已声明：与磁盘原文件同级敏感度） |

**影响**：取证/内存窃取攻击者（转储正在运行的进程、崩溃转储、休眠文件）：
- 拿到一次内存镜像 → 以约 2/3 概率**直接恢复 ECC 长期私钥**（DER 块完整包含
  私钥+公钥）→ 解开该密钥对的所有历史与未来密文，无需口令、无需私钥文件；
- SM2 插件则以约 2/3 概率恢复**单文件 CEK**（配合对应 .encx 即可出明文）；
- 口令永远可从镜像中提取（再配合 .encx 中的盐即可离线验证）。

**定性**：这是 Python 生态 + 第三方库（cryptography/gmssl）的原生缓冲不受
`securemem` 掌控的体现——README 的"能力边界"描述被本测试**物理证实**，
且比文档语气更严重（此前仅是假设，现已确认长期私钥级残留）。

**缓解**：
1. 文档升级为明确警告："解密过文件的进程存续期间，其内存镜像可能含长期私钥/
   CEK；高威胁环境请配合全盘加密 + 进程退出后再离开"；
2. SM2 插件：避免 gmssl `decrypt()` 返回路径的 hex 串——自行实现解密尾段
   （拿到 xy 后用 bytes 直接 KDF/XOR，全程 bytearray，逐块清零）；
3. ECDH/RSA：私钥加载后尽快用完释放（已是现状）；DER 残留属 cryptography
   内部行为，可向上游反馈，或在高威胁场景改用硬件密钥（未来方向）；
4. 长期：将密钥操作移入可清零的原生实现（如 libsodium 封装）。



### F6 🟢 低 / 信息项

- **SM2 解密时序旁路**（a6 D）：纯 Python 标量乘耗时依赖 d 的汉明重量，
  稀疏/稠密密钥实测中位 6.78ms vs 9.82ms（1.45×）。本软件为本地 GUI、
  攻击者无法远程计时，风险低；若未来提供服务化接口需改为常数时间实现。
- **头部明文插件 id**：暴露"用什么算法加密"（流量分析价值有限，容器设计使然）。
- **插件加载 = 任意代码执行**：plugins/ 目录是受信代码区，`.encx` 文件本身
  不会触发代码执行（已确认：容器只解析字节，无反序列化）。保持"插件目录
  仅管理员可写"即可。
- **明文私钥 PEM 默认选项**：无口令时明文落盘（有口令推荐勾选，默认已勾选）；
  README 已说明。
- 实测**未**发现问题：明文残留（容器/密文均无）、salt/nonce/CEK 复用、
  确定性加密、.part 残留（错误/取消/成功三路径）、容器模糊测试（13 类畸形
  输入全部正确报错、无路径穿越）、GCM 块重排（计数器 nonce 正确拒绝）、
  盐篡改（标签拒绝）。
  （注：内存残留由后述 F7 的外部镜像法另行测定，早前同进程扫描结论作废。）

### 5.2 新攻击面扫描结果（全部被拒）

- v2 元数据模糊：ver=1/3 降级、截断、kdf_id=99、iterations=0/1e9 → 全部 IntegrityError；
- 跨插件元数据移植（aes→sm4、rsa→ecdh、sm2→rsa）与同插件跨文件移植 → 全部被拒
  （kdf_id/MAC/盐-密钥绑定）；
- 弱口令密文离线爆破仍可行（12 词字典 1.7s 破出 `123456`）——**这是口令熵的
  物理边界而非缺陷**；GUI 已在创建侧拦截弱口令。

### 5.3 第二轮新发现（低危）

| 编号 | 发现 | 建议 |
|------|------|------|
| N1 | **KDF 迭代数 DoS**：伪造文件把 iterations 改到上界 1e8，受害者需烧约 47.5s CPU 才能发现 MAC 不符（MAC 校验在 PBKDF2 之后，无法先验） | 把 `verify_password_meta` 的迭代上界降到 ~2e7（≈10s），或在 GUI 显示"该文件声明 KDF 轮数异常"供用户中止 |
